# Results

Evaluation outputs for the code-RAG pipeline. Every file here is generated by a
script in `scripts/` — nothing in this folder is edited by hand.

| File | Written by | Holds |
| --- | --- | --- |
| `code_baseline_week1.json` | `scripts/run_baseline.py` | Week 1 baseline: dense top-k retrieval → Gemini |
| `week2_comparison.json` | `scripts/run_comparison.py` | Week 2: top-k vs. MMR vs. facility location |

## Shared setup

Both runs use the same corpus, questions, and retrieval budget, so their numbers
are directly comparable.

- **Corpus** — `data/code_passages.jsonl`: 320 function/class chunks extracted with
  `ast` from the `requests` source tree (`data/build_code_dataset.py`). A chunk's
  `passage_id` is `<file_path>::<node name>`.
- **Questions** — `data/code_questions.jsonl`: 18 hand-written questions about that
  code, each with exactly **one** gold passage id.
- **Retriever** — `all-mpnet-base-v2` embeddings in a FAISS `IndexFlatIP` over
  L2-normalized vectors, i.e. cosine similarity (`retriever/build_index.py`).
- **Budget** — `k = 5` passages handed to the generator for every method.
- **Generator** — `gemini-3.6-flash` via `generator/generate.py`, temperature 0.1,
  `max_output_tokens` 1000, prompted for a 1–2 sentence answer that names the
  relevant functions or classes.

## Metrics

Both files report the two metrics computed by `eval.scorer.evaluate`. They are
**set-based per question and then macro-averaged** over questions:

- `precision@k` — `|retrieved ∩ gold| / |retrieved|`
- `recall@k` — `|retrieved ∩ gold| / |gold|`

Because every question has a single gold passage and `k = 5`:

- `recall@k` is just **the fraction of questions whose gold chunk was retrieved**
  (`recall@k × 18` = number of questions hit).
- `precision@k` is capped at **0.2** — a perfect run cannot score higher, since four
  of the five retrieved chunks are non-gold by construction.

Only *retrieval* is scored. The generated answers are stored but never graded, so
neither file says anything about answer correctness yet.

## `code_baseline_week1.json`

```json
{"results": {"precision@k": 0.0, "recall@k": 0.0}, "predictions": ["..."]}
```

- `results` — metrics dict from `eval.scorer.evaluate`.
- `predictions` — 18 answer strings, in dataset order (`q1` … `q18`).

Run outcome: `precision@k` **0.1630**, `recall@k` **0.7778** — the gold chunk landed
in the top-5 for **14 of 18** questions.

## `week2_comparison.json`

```json
{
  "comparison": {"top_k": {"precision@k": 0.0, "recall@k": 0.0}, "mmr": {}, "facility_location": {}},
  "predictions": {"top_k": ["..."], "mmr": ["..."], "facility_location": ["..."]}
}
```

- `comparison` — one metrics dict per method, from `eval.scorer.compare_methods`.
- `predictions` — one list of 18 answers per method, all in dataset order.

The three methods differ only in *how* the five passages are chosen:

- **`top_k`** — the five nearest neighbours of the question. Same configuration as the
  week 1 baseline, and it reproduces the same numbers.
- **`mmr`** — `selection/mmr.py` over a candidate pool of 15 retrieved passages,
  `lambda_param = 0.5` (equal weight on query relevance and on penalizing the maximum
  similarity to anything already picked).
- **`facility_location`** — `selection/graph_builder.py` builds the full
  passage × passage cosine similarity matrix over the same 15 candidates, then
  `selection/facility_location.py` greedily picks the 5 that maximize total coverage.
  Note this objective looks only at passage–passage similarity: the question is used
  to fetch the candidate pool and is then ignored during selection.

| Method | `precision@k` | `recall@k` | Questions hit |
| --- | --- | --- | --- |
| `top_k` | 0.1630 | 0.7778 | 14 / 18 |
| `mmr` | 0.1444 | 0.7222 | 13 / 18 |
| `facility_location` | 0.0889 | 0.4444 | 8 / 18 |

Plain top-k wins on this dataset. MMR loses one question; facility location loses six.
That is the expected failure mode for a query-agnostic coverage objective on a corpus
of 320 chunks — spreading the budget across the topic space pulls passages away from
the single chunk that actually answers the question. Both diversity methods are also
capped by their candidate pool: neither can ever retrieve a gold chunk that is not in
the top-15.

## Reading these numbers with care

- **n = 18.** One question is worth 5.6 points of `recall@k`, so gaps of a single
  question are noise. The MMR-vs-top-k difference is exactly one question.
- **Duplicate passage ids.** The corpus has 320 rows but only **280 unique**
  `passage_id`s — a name like `auth.py::__init__` collides across classes in the same
  file, so several chunks share an id (`auth.py::__init__` appears 6 times). The FAISS
  index holds all 320 vectors while `retriever/retrieve.py` looks passages up by id,
  so one retrieval can return the same id more than once and `|retrieved|` drops below
  5. This inflates set-based precision: the `top_k` precision total (2.9333) is higher
  than 14 hits × 0.2 = 2.8, which pins it to exactly one hit question yielding only 3
  distinct ids instead of 5. Nothing else in the table is affected — `mmr` and
  `facility_location` totals match their hit counts exactly.
- **Retrieved ids are not persisted.** Only the aggregate metrics and the answer text
  are saved, so per-question hit/miss analysis requires a re-run
  (`python retriever/retrieve.py` prints exactly that for the top-k baseline).
- **Re-runs are not byte-identical.** Retrieval is deterministic, but the generated
  answers are not; a new run overwrites the file in place. The earlier
  `baseline_week1.json` was removed rather than kept when the generator switched to
  `gemini-3.6-flash`.

## Reproducing

Run from the project root — `retriever/retrieve.py` resolves `data/` and
`retriever/` as relative paths.

Build the FAISS index once (needed by both scripts):

```bash
python retriever/build_index.py
```

Then regenerate either file:

```bash
python scripts/run_baseline.py
```

```bash
python scripts/run_comparison.py
```

Generation calls Gemini, so `GOOGLE_API_KEY` must be set in `.env`
(see `.env.example`).
